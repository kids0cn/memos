# 2026-10-15 部署日志：PAT 401 排查 + 全量同步到上游 1511fd1

> 本文记录 10-15 当天的 401 故障排查、两处修复、两次部署与最终全量同步的完整过程。
> 排查中**走过的弯路也如实保留**——它们比结论更值钱。

## TL;DR

- 故障：所有 Personal Access Token 全部 401，session cookie 正常，服务看似"活着但不能用 token"。
- 机制：`PERSONAL_ACCESS_TOKENS` 整行 protojson 解析失败时，**一个坏条目拖垮该用户全部 token**，且旧版本把错误吞成干巴巴的 `authentication required`（零日志）。
- 修复：cherry-pick 上游官方 `#6461`（让错误可见）+ 本仓新增容错降级（让一个坏条目只废一个 token，见 PR [usememos/memos#6478](https://github.com/usememos/memos/pull/6478)）。
- 部署：全量同步上游 30 个提交（含 2 个 CVE、SSRF 修复、Echo→net/http 重构）+ 保留本 fork 的日期导航条，schema `0.31.8 → 26.10.1`，1460 条 memo 零丢失。

## 2. 排查：走通的和走死的

### 2.1 逐段实测（全部通过，反而成了谜团）

| 检查点 | 方法 | 结果 |
|---|---|---|
| SQL 能否匹配 hash | 用真实 SQL 查询原始/修复前/修复后三版 JSON | 三版都命中 |
| protojson 能否解析 | Go 单测 `TestProbePATExpiry` 跑同款 unmarshaler | 三版都 OK，缺 `expiresAt` → `nil` = 永不过期 |
| 原始 JSON 格式 | 备份文件 `PAT_setting_backup.json` 直接跑 `json.loads` + SQL | 合法且命中 |
| 过期判断逻辑 | 读 `authenticator.go:116` | `ExpiresAt != nil && Before(now)`——nil 正确跳过 |
| Store 层包装 | 读 `store/user_setting.go` | 无额外过滤/过期检查 |

**分段全对，生产却稳定 401**——说明故障不在数据、不在静态逻辑，而在某条**运行时路径**，且旧版不留任何日志。

### 2.2 被自己的实验推翻的假设

**假设：缺 `expiresAt` 导致 Go 零值时间被判定过期。**

依据看似充分：补上字段后立刻 200。但随后做了受控实验：

```
A.  有 expiresAt, 未重启   → 200
B1. 移除 expiresAt, 未重启 → 200   ← "坏"状态也能用
B2. 移除 expiresAt + 重启  → 200   ← 清缓存也一样
C1/C2. 恢复 + 重启         → 200
```

**结论：`expiresAt` 不是根因**，18:5x 那次 `UPDATE` 覆盖整行 JSON 本身就是恢复动作。教训：**单次"修好了"不能证明因果**，必须做移除/复现的反向实验。

## 3. 根因机制（已确认）

```
PERSONAL_ACCESS_TOKENS 整行 JSON 中出现任意非法字段
（例：createdAt 不是合法 RFC3339 时间）
        ↓
protojsonUnmarshaler.Unmarshal(整行) 返回 error
        ↓
GetUserByPATHash 返回 err
        ↓
旧版：resolveBearer 吞掉 err → 返回 (nil,nil)
        → 401 authentication required，零日志（"silent 401"）
新版：slog.Error + 完整调用栈 + 具体非法值
```

**致命放大**：解析是**整行**进行的——所以**一个**坏条目会让该用户**所有** token 一起失效，包括用户根本没碰过的那把。

上游 postgres 驱动的注释表明他们已防了**跨用户**污染（"keeps one user's corrupt setting from blocking every other user's token"），但**单用户内部**无人设防——这正是本次新增修复针对的洞。

**触发来源未 100% 钉死**（坏数据在修复时已被覆盖，无法回溯）。最可能是服务写 `lastUsedAt` 与外部写入的并发竞争——**此为推测，未复现**。现在的日志会在下次发生时直接给出元凶。

## 4. 两处修复

### 4.1 上游官方修复（cherry-pick `2487db7` → 本仓 `c66dfaf`）

`fix(auth): surface PAT store failures instead of a silent 401 (#6461)`

- 新增哨兵错误 `auth.ErrInvalidPAT`，区分"token 无效" vs "存储查询失败"
- `sql.ErrNoRows` → `(nil, nil)`；其余存储错误向上传播
- `Authenticate` 对存储失败打 `slog.Error`

价值：**把不可见变成可见**。有这条日志，本故障 10 分钟可定位，无需反向工程。

### 4.2 本仓新增：容错降级（→ PR #6478）

`store/personal_access_tokens.go` 的 `ParsePersonalAccessTokens`：

1. 先整行解码（原路径，快）；
2. 整行失败时，退化为**逐条解码**：保留仍能解码的条目、丢弃坏的、`slog.Warn` 记录其索引与原因；
3. 信封本身损坏（JSON 结构坏）才返回原错误。

三个驱动（sqlite/mysql/postgres）统一改调该函数。行为：

```
WARN skipped corrupt personal access tokens kept=1 skipped=1
cause="token[0]: proto: invalid google.protobuf.Timestamp value \"...\""
```

即：**一把 token 坏 → 只废这一把**，其余照常工作，且日志直接告诉你删哪把重建。

测试：`store/personal_access_tokens_test.go` 覆盖 5 种场景（正常、坏条目被跳过且好条目存活、坏条目自身 hash 查不到、全坏、信封坏）。

## 7. 教训

1. **浅克隆制造假冲突**：`--depth` fetch 的 upstream 与本地无共同祖先，cherry-pick 会报几百个 `AA (add/add)`。`git merge-base` 为空即可确诊，`git fetch --unshallow` 解决。
2. **单次成功 ≠ 因果**：补字段后 200 就下结论，被反向实验证伪。修复类假设必须能**复现**再**移除**验证两次。
3. **静默失败最贵**：本故障耗时约 6 小时主因是旧版零日志。遇到"看似随机的 401"，先问"日志里有什么"，没有日志就是第一个要修的东西。
4. **`store/test` 需要 Docker**：本机无 Docker → Testcontainers 卡死 11 分钟后被杀（`FAIL store/test`），属环境限制非代码问题；sqlite 路径（生产所用）测试全绿。
5. **凭据不进仓库**：本次涉及的 GitHub PAT / memos PAT 一律走 `~/.hermes/memos-data/*.txt` 文件读取，`git remote` 与 commit 内容均不含凭据。
